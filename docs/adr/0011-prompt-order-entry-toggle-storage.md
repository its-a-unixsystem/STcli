# Store Prompt Order Entry toggles at preset level; vendor ecosystems live in plugins

Flipping a Prompt Order Entry's enabled flag edits the preset itself: each flip produces a new immutable Artifact Revision and re-pins only the session it was made from, through a new Session Configuration Revision. Completed turns and past Generation Attempts are never affected, and other sessions keep their pinned revision until the preset is re-selected there — a deliberate divergence from live SillyTavern, where editing the preset file immediately affects every chat. Session-level toggle overrides were rejected as the storage model (a new domain concept that diverges from SillyTavern, where toggles live in the preset file); a layered preset-plus-session-override model was deferred, not rejected, and is scheduled as prompt-order-toggles issue 02.

Two boundary decisions accompany this. First, core implements base SillyTavern only: community/vendor ecosystem behavior — concretely NemoPresetExt's `{{// @... }}` prompt directives — is customization and ships as plugins on a session-independent, artifact-inspecting plugin surface, never as hardcoded core logic. The directive parsing that previously lived in `preset_compatibility_warnings` (the `prompt-directives-not-evaluated` warning) was ruled a bug under this principle and is removed (issue 06); directive evaluation returns as a default-bundled plugin (issues 03–05). Second, the TUI is the guardrail layer: the engine and CLI stay permissive per Compatibility Profile parity, while the UI surfaces Compatibility Warnings (for example when a structural marker such as `chatHistory` is disabled) and applies radio auto-flip semantics for exclusivity groups.

Consequences: one small content-addressed revision per flip (identical change sets deduplicate); the engine's toggle operation accepts a *set* of identifier→enabled changes applied atomically so that radio auto-flips remain a single revision when the directives plugin lands.
